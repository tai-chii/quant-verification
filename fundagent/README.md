# fundagent — ニュースから売買仮説を出し、その的中率を実測するシステム

ファンダメンタルズのニュースを定期的に集め、LLMで「銘柄・方向・確度」に構造化して提案し、
**後からその提案の成績を自動で検証する**プロトタイプ。

主役は提案ではなく **検証** のほう。提案だけなら誰でも作れるが、
「その提案に意味があったか」を測る仕組みがないと、ただの占いになる。

## 使い方

```bash
python run.py cycle              # 収集→選別→抽出→集約→レポート（通常はこれ）
python run.py cycle --dry-run    # APIを叩かずに配線確認（キー不要・無料）
python run.py verify             # 期間が満了したシグナルの損益を確定
python run.py stats              # 的中率・超過リターン・有意性を集計
python run.py calibrate          # スコア分布からしきい値を決め直す
python run.py weights            # 情報源ごとの実績から重みを測り直す
```

運用リズムの目安: `cycle` を1日2〜3回（寄り前・引け後・夜）、`verify`・`stats` を週1回、
`weights` と `calibrate` を月1回。

## パイプライン

```
[1] collect  公開RSS/API から記事メタを取得（本文の複製はしない）
                 ↓
[2] triage   安いモデルで「そもそも売買材料か」を選別（8割ここで落ちる）
                 ↓
[3] extract  賢いモデルで 銘柄/方向/確度/織り込み度 をJSON抽出
                 ↓
[4] aggregate 銘柄×期間で合成 → スコア → Tier A/B/C
                 ↓
[5] report   Obsidian にレポート + 台帳CSV追記
                 ↓  （時間が経ってから）
[6] verify   翌営業日の始値で入り、N営業日後の終値で出た場合の損益を確定
[7] stats    Tier別の的中率・超過リターン・t値・前半/後半OOS
```

### スコアの定義（意図的に単純にしてある）

```
edge_i   = (confidence - 0.5) * 2 * (1 - priced_in)
weight_i = tier_weight(情報源) * 2^(-経過時間 / 半減期)
net      = Σ sign_i * edge_i * weight_i          # long:+  short:-
score    = |net| ,  direction = sign(net)
```

`priced_in`（既に価格に織り込まれている度合い）で割り引くのが要。
公開ニュースの大半は既に織り込み済みなので、ここを正直に高く見積もらないと
「誰でも知っている話」を有望シグナルとして拾ってしまう。

独立ソース数は `cluster_id`（見出し類似で束ねた単位）で数える。
同じ通信社の配信が複数媒体に載ったものを2件と数えないため。

## 情報源の信頼度を実績で決める

`tier_weights`（S=1.0, A=0.7 …）は最初に勘で置いた値でしかない。
これを実測に置き換えるのが `run.py weights`。

### どう測るか

集約後の `signals` は複数ソースが混ざっているので、ソース別の成績は測れない。
そこで **`raw_signals`（1記事＝1ソースの単独主張）を個別に評価**する。
「そのソースの言うとおりに毎回入っていたら、超過リターンはいくつだったか」を直接測る。
追加のLLMコストはゼロ（抽出済みのデータを別の切り口で集計するだけ）。

### 経験ベイズで先入観から実績へ乗り換える

```
λ      = n / (n + k)                    # k = 事前分布の強さ（既定30）
w_ev   = 1 + 平均超過リターン / sd_pool   # 実績だけから決まる重み。tier を見ない
weight = clip((1-λ) * 事前重み + λ * w_ev, floor, cap)
```

- `n=0` → λ=0 → tier の初期値そのまま（コールドスタートが滑らか）
- `n≫k` → λ→1 → tier は消え、**実績だけが重みを決める**

この形なので、**tier C の個人ブログでも実績を積めば tier S を追い越せる**し、
tier S でも成績が悪ければ下がる。tier は初期値であって結論ではない。

n=5 で平均+2%の発信者にいきなり重み2.0を与えたら運を増幅する装置になる。
縮約はそれを防ぐためにある。n が k を超えるまで重みはほとんど動かない——それが正しい挙動。

`weights` の出力は `config/source_weights.yaml`（自動生成・手編集しない）に落ち、
次回以降の `cycle` で `aggregate` が自動的に読む。

### 逆張り候補は自動適用しない

継続的にマイナスの超過リターンを出すソースは検出してレポートに出すが、**符号は自動反転しない**。
偶然の連敗と本物の逆相関は n が十分でも見分けにくく、反転を自動化すると壊れ方が読めなくなる。

## 二次情報（相場観ブログ）の足し方

`sources.yaml` に `role: opinion` を付けると、triage / extract の挙動が変わる:

- **書き手が明示した方向だけを抜く。** 書かれていない方向をこちらで推論しない。
- 「〇〇を上抜けたら買い」のような条件付きの見解は、条件成立を判定できないので出さない。
- `confidence` は書き手の断定の強さではなく、こちらから見た主張の確からしさ。
- `priced_in` は「その見解が既にコンセンサス化しているか」と読み替える。

足すときの最低条件:

1. robots.txt で禁止されていない（`collect` が全取得で自動確認する）
2. 方向が明示されている（「押し目買い」「〇〇まで下落を想定」など）
3. 更新が定期的（月に数本では、重みが動くまで何年もかかる）
4. 後出しでない（相場が動いた後の解説記事は的中率を測れない）

RSSがあるサイトは `kind: rss` で足すだけ。RSSがないサイトは `kind: html_list` に
CSSセレクタを書く（サイト改修で壊れるので、壊れたら直すか `enabled: false` で切る）。
本文は取得も保存もしない——見出しとリンクだけ。

**生存者バイアスに注意**: 成績の悪い発信者は黙って消える。
消えたソースを履歴から削除すると、残った側の成績が実力より良く見える。
`source_scores` テーブルは履歴を残すので、消したソースの記録も残しておくこと。

## 設計上の防護柵

1. **先読みをしない。** `signals.decided_at` より後の価格でしか評価しない。
   エントリーは翌営業日の始値（判定した瞬間の価格では約定できないため）。
2. **コストを必ず引く。** 日本株0.20%/指数0.10%/FX0.02%（往復、`config.yaml`）。
3. **ベンチマークを引く。** TOPIX連動ETFの同期間リターンを引いた超過リターンを併記。
   市場全体の上昇を自分のエッジと誤認しないため。
4. **帰無仮説を併記する。** 「方向を無視して常に買った場合」を同時に計算する。
   これを超えなければ方向判定に意味はなかった。
5. **前半/後半に割る。** 前半で見えた効果が後半で消えたら採用しない。
6. **しきい値を勘で決めない。** `calibrate` でスコア分布から決める。
7. **提案ゼロを正常な結果として扱う。** 無理に出すほうが検証を汚す。
8. **情報源の重みを勘で決めない。** `weights` で実績から測る。ただし n が少ないうちは縮約で動かさない。
9. **robots.txt を毎回確認する。** 禁止されている先は取得しない。

## 情報源について

`config/sources.yaml` に載せるのは **配信目的で公開されているフィード/API だけ**。

- 有料記事の本文取得・保存はしない（日経など）。規約違反であり、法的リスクがある。
- robots.txt で禁止されたページのスクレイピングもしない。
- 代わりに **一次情報** を軸にする。日銀・FRB・TDnet適時開示は無料で、
  かつ「報道より早い」ので、信頼度でも速度でも有料媒体の後追いより有利。

tier は S=一次情報 / A=通信社・公共放送 / B=経済メディア / C=参考。

## 既知の限界（正直に）

- **公開ニュースはほぼ瞬時に織り込まれる。** このシステムに構造的な優位があるとすれば、
  (a) 適時開示のように「出た直後で人間が読み切れていない」もの、
  (b) 決算後の緩やかなドリフト(PEAD)、(c) 複数ソースの突き合わせ、のいずれか。
  単なるニュース要約に優位はない。**それを確かめるのが verify の役割。**
- LLMの `confidence` は較正されていない。数値そのものを信用せず、
  実測の的中率との対応を見てから使う。
- 現状は日足ベース。日中の値動きは見ていない。
